## TODO-001: Git Webhook 自动触发

- **What:** 暴露签名验证的 Webhook 端点（如 `/webhooks/github`、`/webhooks/gitlab`、`/webhooks/gitea`），支持 push/tag 事件自动触发构建。
- **Why:** 当前用户必须手动打开浏览器点击"构建"。Webhook 是实现"自动化 CI/CD 体验"的最小一步，也是从"手动工具"升级为"基础设施"的关键分水岭。
- **Pros:** 用户 push 代码后即可自动构建；为后续 cron 触发、PR 预览构建打下基础；实现成本低（一个 Flask 路由 + HMAC 验证）。
- **Cons:** 需要处理不同 Git 提供商的 payload 签名差异；需要向用户解释如何在 Git 平台配置 webhook URL。
- **Context:** 已在 CEO review 中评估为 Proposal 1， deferred 至 Phase 2。API 设计时应预留 webhook 配置的 JSON 字段（Project.triggers）。
- **Effort estimate:** S (~1d human / ~20m CC)
- **Priority:** P1
- **Blocked by:** TASK-005 (Build Management), TASK-004 (Project Management)

## TODO-003: 修复开发环境下 WebSocket console 报错 (flask-sock + Werkzeug)

- **What:** 构建详情页 (`/builds/:id`) 在 Chromium 浏览器下会出现 `WebSocket connection failed: Invalid frame header` 的 console 错误。
- **Why:** 这是 `flask-sock` 与 Werkzeug 开发服务器的已知兼容性问题：WebSocket 连接关闭后，Werkzeug 会向同一 socket 写入 HTTP 响应头，导致 Chromium 解析为非法帧。
- **Fix:** 生产环境部署时切换到 Gunicorn 即可消除；如需在开发环境也消除，可迁移到 `Flask-SocketIO` 或在前端捕获抑制该错误。
- **Found by:** /qa on mvp01, 2026-04-03
- **Priority:** P3 (low — 有轮询 fallback，不影响核心功能)
